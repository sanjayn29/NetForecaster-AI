## 2. Data Nature

This is **flow-level** data generated by **CICFlowMeter**. Each row represents one network flow (a bidirectional aggregation of packets between a source and destination). This is **NOT** packet-level (pcap) data.

Key implications:
- No raw packet payloads are available.
- Features are pre-aggregated statistics per flow (packet counts, byte counts, IAT statistics, flag counts, etc.).
- Scapy/PyShark are not needed — these CSVs are the primary data source.

## 10. Potential Data Leakage Columns

| Column | Leakage Risk | Rationale |
|--------|-------------|-----------|
| `Flow ID` | **HIGH** | Direct flow identifier — encodes IP+port+protocol. Only in Tuesday file. |
| `Src IP` | **HIGH** | Attack sources likely have fixed IPs in lab environment. Only in Tuesday file. |
| `Dst IP` | **HIGH** | Attack targets are fixed in lab setup. Only in Tuesday file. |
| `Src Port` | **MEDIUM** | Ephemeral ports may correlate with attack tools. Only in Tuesday file. |
| `Dst Port` | **MEDIUM** | Certain ports are strongly associated with specific attacks (e.g., port 22 → SSH brute force). Present in all files. |
| `Label` | **N/A** | Target variable — must never be used as a feature. |

**Mitigation:**
- `Flow ID`, `Src IP`, `Dst IP` must be excluded from feature vectors (but can be used for graph construction).
- `Dst Port` and `Src Port` can be used as features but require careful monitoring for overfitting.
- `Protocol` is a legitimate feature with low leakage risk.

## 11. Feasibility Assessment

### 11.1 Temporal Forecasting — FEASIBLE

| Criterion | Assessment |
|-----------|-----------|
| Timestamps available? | **YES** — `Timestamp` column in all files |
| Chronological ordering possible? | **YES** — timestamps are parseable datetime strings |
| Multiple time periods? | **YES** — 10 different days spanning ~17 calendar days |
| Attack patterns vary over time? | **YES** — each day has different attack types |
| Intra-day temporal structure? | **YES** — flows are timestamped within each day (~01:00–13:00) |

**Approach:** Temporal windows can be constructed by sorting flows chronologically. The chronological train/validation/test split should respect day boundaries to prevent information leakage.

**Limitation:** The data covers only ~12 hours per day. Inter-day gaps (weekends, missing weekdays) mean we cannot model continuous 24/7 network evolution. The forecasting model will primarily learn *intra-day* temporal dynamics and *across-day* attack pattern evolution.

### 11.2 Graph Construction — PARTIALLY FEASIBLE

| Criterion | Assessment |
|-----------|-----------|
| Source IP available? | **ONLY in 1/10 files** (Tuesday) |
| Destination IP available? | **ONLY in 1/10 files** (Tuesday) |
| Dst Port available? | **YES** — all 10 files |
| Protocol available? | **YES** — all 10 files |

**Full IP-based graph (Src IP → Dst IP):**
- Only feasible for the Tuesday file (7.9M rows).
- Tuesday sample: 32 unique Src IPs, 5 unique Dst IPs (small lab network).

**Port/Protocol-based graph (alternative for all files):**
- Nodes can be defined as (Dst Port, Protocol) service endpoints.
- Edges represent flows between services.
- 37,304 unique Dst Ports observed, 3 protocols (TCP=6, UDP=17, HOPOPT=0).
- Top destination ports: 8080, 53, 3389, 80, 443, 445.

**Recommended approach:** Design a dual-mode graph builder:
1. **IP-graph mode** when Src IP/Dst IP are available.
2. **Service-graph mode** using Dst Port + Protocol as node identifiers when IP is unavailable.
3. Clearly document the limitation that 9/10 files lack IP information.

## 13. Important Limitations

1. **No packet-level data.** All features are pre-aggregated per flow. Deep packet inspection or payload analysis is not possible.

2. **IP addresses available in only 1/10 files.** Full network graph construction (host-to-host) is limited to the Tuesday file. An alternative service-graph approach is needed for the other 9 files.

3. **Lab environment.** CIC-IDS2018 was captured in a controlled AWS environment. The network topology is small (5 destination IPs, ~32 source IPs in the Tuesday file). Real-world generalization should not be assumed.

4. **Each day has a single attack scenario.** There is no overlap of attack types within a single day. This simplifies detection but makes cross-day forecasting the primary research question (predicting whether the next time window will transition from benign to attack, and what type).

5. **~12 hours of data per day.** No nighttime traffic. Inter-day gaps exist. Continuous temporal modeling requires acknowledging these gaps.

6. **Severe class imbalance.** Some attack types have fewer than 100 samples (SQL Injection: 87, Brute Force -XSS: 230). Stratification and careful metric selection are essential.

7. **Attack stage labels are inferred, not ground truth.** The mapping from attack type to kill chain stage is a best-effort approximation based on attack semantics.

8. **Row count artifacts.** Several files have exactly 1,048,575 rows (= 2^20 - 1), suggesting possible truncation by Excel or CSV export tools. The original CIC-IDS2018 dataset may contain more rows per day.

9. **Duplicate flows may be legitimate.** High duplicate rates in brute-force/SSH days may reflect actual repeated attack patterns rather than data errors. Deduplication decisions should be documented.

10. **The `Flow Byts/s` and `Flow Pkts/s` columns are derived features** computed as bytes/packets divided by flow duration. When flow duration is zero, these become NaN or Inf. These can be recomputed or imputed rather than dropped.
